# گزارش اصلاحات بک‌اند ArkaLearn

تاریخ شروع بازبینی: ۲۶ اکتبر ۲۰۲۶؛ به‌روزرسانی نهایی: ۱۱ نوامبر ۲۰۲۶. این گزارش تغییرات کد محلی را توضیح می‌دهد. استقرار روی سرور و اجرای Migration روی دیتابیس عملیاتی انجام نشده است. جزئیات رفع مانع مجوز در `backend-image-validation-2026-11-11.fa.md` ثبت شده است.

## اصلاحات انجام‌شده

### پرداخت، کیف پول و خرید

- درخواست پرداخت پیش از فراخوانی درگاه در `Finance.PaymentAttempts` ذخیره می‌شود. مبلغ، ارائه‌دهنده، سفارش، کاربر و مقصد پرداخت از داده ثبت‌شده سرور خوانده می‌شوند.
- Callback باید با شناسه پرداخت، مبلغ و در صورت بازگشت از درگاه، شماره سفارش تطبیق داشته باشد. شماره مرجع تکراری با محدودیت یکتای دیتابیس رد می‌شود.
- پردازش هم‌زمان یک پرداخت با قفل زمانی دیتابیس محدود می‌شود. نتیجه موفق ذخیره می‌شود تا Callback تکراری، تحویل دوباره ایجاد نکند.
- تأیید موفق درگاه جداگانه ذخیره می‌شود؛ شکست تحویل، امکان تلاش مجدد بدون تأیید دوباره درگاه را حفظ می‌کند.
- تحویل خرید و تکمیل وضعیت پرداخت در یک تراکنش انجام می‌شوند. خرید با کیف پول نیز کسر موجودی و ثبت نتیجه تجاری را در تراکنش مشترک انجام می‌دهد؛ شکست، تغییرات ذخیره‌شده همان تراکنش را برمی‌گرداند.
- فیلدهای موجودی کیف پول و جمع مالی مرتبط، کنترل هم‌زمانی EF دارند. اعتبار فروش مدرس داخل تراکنش اجرا می‌شود.
- Handlerهای `InvoicePaid` خطا را به پردازشگر برمی‌گردانند. Outbox فقط پس از موفقیت، رویداد را پردازش‌شده ثبت می‌کند. اجرای Handlerهای مشترک DbContext ترتیبی شده و پردازش مالی Outbox از قفل تراکنشی SQL Server استفاده می‌کند.
- سبد خرید چندقلمی، همه اقلام را در Projection برمی‌گرداند.

### اتاق‌های آنلاین

- ورود به MeetingHub به Join Ticket معتبر و امضاشده نیاز دارد؛ نقش و شناسه شرکت‌کننده از Ticket استخراج می‌شوند. اتاق حذف‌شده یا غیرفعال نمی‌تواند پذیرای اتصال جدید باشد.
- اتصال جایگزینِ همان شرکت‌کننده می‌تواند به اتاق پر برگردد؛ قطع اتصال قدیمی، حضور اتصال جدید را پاک نمی‌کند.
- شرکت‌کننده منتظر پذیرش، مجوز انتشار پیام و رسانه در اتاق اصلی ندارد. Signal بین دو اتاق رد می‌شود و نام فرستنده از اطلاعات ثبت‌شده خوانده می‌شود.
- قطع موقت میزبان، مهلت ۳۰ ثانیه‌ای برای اتصال مجدد دارد. بازگشت میزبان پایان خودکار را لغو می‌کند. پایان جلسه، وضعیت صندلی‌ها و عضویت گروه‌های اصلی و انتظار را پاک می‌کند.
- ChatHub و API قدیمی پیام‌ها احراز هویت و بررسی دسترسی اتاق دارند؛ دسترسی پیش از خواندن Cache و پیام‌ها بررسی می‌شود.
- توکن جدید صندلی، شناسه اتاق و صندلی و `identityScope=room-seat` دارد. استفاده از آن در APIهای حساب و پرداخت و Hubهای نامرتبط رد می‌شود؛ مسیر مشخص خروج از اتاق مجاز است.
- خروج و آفلاین‌کردن صندلی به بررسی دسترسی نیاز دارد؛ کاربر صندلی برای تغییر وضعیت صندلی دیگر به مجوز مدیریت نیاز دارد.
- صفحه‌بندی پیام‌ها در SQL انجام می‌شود؛ نام فرستنده با بارگذاری همه کاربران به دست نمی‌آید. اندازه صفحه محدود است.

### امنیت و زیرساخت

- رمزهای جدید با PBKDF2-SHA256 و Salt تصادفی ذخیره می‌شوند. رمزهای قدیمی هنگام ورود موفق به قالب جدید ارتقا می‌یابند. رمز خام در رویدادهای ورود و ایجاد کاربر درج نمی‌شود.
- ذخیره جدید اسرار پرداخت و کلیدهای محتوای DRM از AES-GCM استفاده می‌کند. کلید ثابت عمومی حذف شده و خواندن داده قدیمی فقط با کلیدهای صریح پیکربندی‌شده ممکن است.
- اعتبارسنجی گواهی SMTP در محیط عملیاتی فعال است؛ حتی Override دیتابیس نمی‌تواند استثنای Development را در Production فعال کند.
- صفحه خطای توسعه و جزئیات خطای SignalR به Development محدود شده‌اند. اعتبارسنجی MVC بازگردانده شده، اولویت Bearer header اصلاح شده و توکن Query فقط در مسیرهای Hub پذیرفته می‌شود.
- ارجاع‌های مستقیم به DLLهای Debug با ProjectReference جایگزین شده‌اند؛ ارجاع‌های تکراری JWT حذف شده‌اند.
- AutoMapper به `16.2.0` ارتقا یافته و Adapter محلی جایگزین وابستگی قدیمی شده است. خواندن تنظیم قدیمی `AssmblyNamesForLoadProfiles` حفظ شده است.
- ImageSharp با `SkiaSharp 4.155.0` جایگزین شده و وابستگی به مجوز Six Labors حذف شده است. Azure.Identity به `1.17.1`، Pkcs به `10.0.13` و بسته بومی SQLite تست‌ها به شاخه اصلاح‌شده ارتقا یافته‌اند. FluentValidation از نسخه Preview به `11.11.0` سازگار با مصرف‌کنندگان موجود منتقل شده است. بسته قدیمی SignalR `1.2.0` نیز با FrameworkReference به `Microsoft.AspNetCore.App` جایگزین شده است.
- Snapshot خالی EF از مدل فعلی بازسازی شده است. Migration موقت تولید مدل حذف شده و فقط Snapshot نگه داشته شده است؛ هیچ Migration ایجادکننده کل دیتابیس اضافه نشده است.
- Factory طراحی EF به Connection String صریح نیاز دارد و برای ابزار Migration، API یا Workerهای آن را اجرا نمی‌کند. نادیده‌گرفتن هشدار تغییر مدل حذف شده است.

## وضعیت اعتبارسنجی

آخرین اجرا روی خروجی Release: **۸۲ آزمون موفق، صفر شکست و چهار آزمون SMTP اجرا‌نشده**؛ شامل ۷۱ آزمون واحد موفق و ۱۱ آزمون Integration موفق. نتیجه در `backend-hardening-tests.log` ثبت شده است. تست‌های پرداخت از SQLite واقعی در حافظه استفاده می‌کنند و بازگشت تراکنش، Callback تکراری، تطبیق مبلغ و سفارش، یکتایی مرجع و قفل پردازش را پوشش می‌دهند. آزمون‌های Hub از Mock استفاده می‌کنند؛ اجرای مرورگر و WebRTC واقعی سه کلاینت انجام نشده است.

چهار آزمون SMTP واقعی به‌صورت پیش‌فرض Skip می‌شوند. اجرای آن‌ها نیازمند `ARKALEARN_RUN_LIVE_SMTP_TESTS=1` و تنظیمات SMTP است.

بررسی `dotnet ef migrations has-pending-model-changes --no-build` با نتیجه موفق تمام شد. اسکریپت `backend-payment-attempts.sql` با ارائه‌دهنده SQL Server و بدون اتصال به دیتابیس تولید شد. اجرای عملی قفل `sp_getapplock`، رقابت تراکنش‌ها و Migration روی SQL Server هنوز نیازمند محیط آزمایشی است.

گزارش `backend-dependency-audit.json` شامل نسخه‌های Resolveشده و هشدارهای Restore است. در آخرین Restore، هشدار آسیب‌پذیری `NU19xx` وجود نداشت. یک `NU1608` باقی مانده است: Parrot 2.0 به بسته قدیمی AutoMapper DI وابسته است. Assetهای آن بسته صریحاً حذف شده‌اند و از DI جدید AutoMapper استفاده می‌شود؛ هشدار پنهان نشده است. رفع این قید در خود Parrot به انتشار نسخه اصلاح‌شده آن نیاز دارد. آزمون Mapping، ثبت Parrot و نگاشت Adapter را بررسی می‌کند.

ساخت Release و تست‌های همان خروجی موفق شدند. با اعلام نبود کلید Six Labors، استفاده محدود از ImageSharp به SkiaSharp منتقل شد و دیگر به آن کلید نیازی نیست. مجوز AutoMapper جداگانه است و باید در محیط اجرای API تنظیم شود. هشدارهای قدیمی Nullable و سایر هشدارهای کامپایل به‌طور کامل رفع نشده‌اند.

## پیش‌نیازهای استقرار

۱. ابتدا از دیتابیس و کلیدهای فعلی نسخه پشتیبان تهیه و تغییرات را روی دیتابیس آزمایشی بررسی کنید. جدول `Finance.PaymentAttempts` باید پیش از راه‌اندازی نسخه جدید ساخته شود. اسکریپت تولیدشده مخصوص دیتابیس موجود دارای `__EFMigrationsHistory` است؛ اسکریپت نصب دیتابیس تازه نیست.

۲. پیش از انتشار، پرداخت‌های باز نسخه قدیمی را تعیین تکلیف کنید. Callback قدیمی فاقد رکورد PaymentAttempt از روی اطلاعات Query بازسازی یا تأیید نمی‌شود. تغییر قیمت یا تنظیمات درگاه در زمان پرداخت باز ممکن است تحویل را متوقف کند؛ مرجع تأییدشده برای پیگیری باقی می‌ماند.

۳. کلیدهای تصادفی ۳۲ بایتی با قالب Base64 را در تنظیمات امن محیط قرار دهید:

| کاربرد | تنظیم استاندارد .NET / متغیر محیطی |
| --- | --- |
| اسرار درگاه | `PaymentGateway__SecretsMasterKeyBase64` یا `ARKALEARN_PAYMENT_SECRETS_KEY` |
| کلیدهای DRM | `DesktopDrm__MasterKeyBase64` یا `ARKALEARN_DRM_MASTER_KEY` |
| کلیدهای قبلی اسرار درگاه | `PaymentGateway__PreviousMasterKeysBase64__0` و اندیس‌های بعدی |
| کلیدهای قبلی DRM | `DesktopDrm__PreviousMasterKeysBase64__0` و اندیس‌های بعدی |
| امضای Ticket اتاق | `RoomJoinTicket__SigningKey`، با حداقل ۳۲ بایت UTF-8 |
| مجوز AutoMapper | `AutoMapper__LicenseKey` در محیط اجرای API |
| اتصال ابزار EF | `ARKALEARN_MIGRATION_CONNECTION`؛ فقط برای ابزارهای EF |

مقدار کلیدها نباید در سورس، لاگ یا چت درج شود. کلیدهای قدیمی واقعی باید پیش از تغییر کلید جاری به Key Ring افزوده شوند. برای داده‌ای که قبلاً با Fallback توسعه رمز شده، کلید مشتق‌شده همان نسخه قبلی باید صریحاً و موقتاً در Key Ring تعریف و داده با کلید جدید بازنویسی شود. حذف کلید قبلی پیش از مهاجرت داده، دسترسی به اسرار یا محتوای قبلی را قطع می‌کند. صرف تغییر کلید جاری، بازنویسی خودکار داده قدیمی انجام نمی‌دهد.

۴. برای حذف اعتبار توکن‌های صندلی قدیمی که فاقد Scope بودند، کلید امضای JWT در استقرار امن تعویض و ورود مجدد کاربران انجام شود. کلاینت‌ها باید Ticket جدید دریافت کنند. کلید Ticket مستقل از JWT ترجیح دارد؛ در نبود آن، کلید معتبر JWT استفاده می‌شود.

۵. ساخت Release به کلید Six Labors نیاز ندارد. برای بازتولید اعتبارسنجی اجرا کنید:

```powershell
dotnet restore BackEnd/ArkaSoftware/ArkaSoftware.sln
dotnet test BackEnd/ArkaSoftware/ArkaSoftware.sln --no-restore --nologo
dotnet build BackEnd/ArkaSoftware/ArkaSoftware.sln -c Release --no-restore --nologo
dotnet test BackEnd/ArkaSoftware/ArkaSoftware.sln -c Release --no-build --no-restore --nologo
```

۶. برای اتاق‌ها، سناریوهای ورود مدرس و دانشجو، انتظار و پذیرش، قطع و اتصال مجدد، تب دوم، پایان جلسه، پیام و رسانه بین اتاق‌ها و پایان زمان جلسه روی کلاینت‌های واقعی اجرا شوند. ساختار حضور اتاق همچنان حافظه‌ای و محدود به یک فرایند API است؛ اجرای چند نمونه API به طراحی حضور و قفل توزیع‌شده نیاز دارد.

## محدودیت‌های باقی‌مانده

- ۱۲ Migration قدیمی دارای Metadata کامل کشف EF نیستند؛ فهرست در `backend-migration-discovery-review.json` آمده است. افزودن خودکار Metadata می‌توانست Migrationهای قبلاً دستی اجراشده را دوباره فعال کند؛ این فایل‌ها بدون مقایسه با تاریخچه دیتابیس تغییر نکردند. بنابراین نصب کامل دیتابیس تازه و ارتقای کل زنجیره Migrationها هنوز تأیید نشده است.
- Snapshot فعلی با مدل C# سازگار است؛ این به معنی سازگاری طرح دیتابیس واقعی با مدل نیست.
- آزمون هم‌زمانی با SQL Server، تحویل واقعی دوره/DRM، پرداخت در محیط Sandbox و آزمون سرتاسری اتاق‌ها باقی مانده‌اند.
- Outboxهای معیوب برای Retry باقی می‌مانند و نیازمند پایش و تعمیر هستند؛ تعداد زیاد رویداد خراب در ابتدای صف می‌تواند پردازش رویدادهای بعدی را به تأخیر بیندازد.
- کنترل جامع دسترسی تمام عملیات مدیریتی RoomController و همه APIهای سامانه، اندازه‌گیری Coverage و آزمون بار، فراتر از آزمون‌های افزوده‌شده این مرحله است.
- نسخه‌های Runtime نصب‌شده روی ماشین توسعه از وصله امنیتی ASP.NET Core منتشرشده در ۱۰ نوامبر ۲۰۲۶ قدیمی‌ترند. پیش از استقرار این API با هدف net9.0، Runtime/Hosting Bundle نسخه `9.0.23` یا نسخه اصلاح‌شده جدیدتر در همان شاخه نصب شود. برای اجرای تست‌های net10.0، نسخه اصلاح‌شده `10.0.15` یا جدیدتر لازم است. در این مرحله Runtime سیستم نصب یا تعویض نشده است.
- جابه‌جایی گسترده پیاده‌سازی‌های زیرساختی از API به پروژه‌های مستقل انجام نشده است؛ برای جلوگیری از تغییر معماری وسیع، قراردادها و سرویس‌های لازم در همین ساختار اصلاح شدند.

## فایل‌های بازبینی

اصلاحات محدود اتصال اتاق در ۱۱ نوامبر، نتیجه آزمایش مسیر عمومی و مراحل تأیید در شبکه دانشجو در `online-room-connection-2026-11-11.fa.md` آمده‌اند. تفاوت این مرحله نسبت به وضعیت محلی پیش از آن در `online-room-connection-changes.diff` ثبت شده است.

`backend-hardening-files.json` فهرست فایل‌های بازبینی‌شده و SHA-256 آن‌ها را دارد. `backend-hardening-existing-files.diff` تفاوت فایل‌های دارای نسخه پشتیبان محلی را نشان می‌دهد؛ جایگزین diff مخزن Git نیست و فهرست کامل فایل‌های جدید محسوب نمی‌شود. فایل‌های تنظیمات حاوی اسرار در این diff کپی نشده‌اند. در ریشه پروژه، مخزن Git شناسایی نشد و Commit یا Push انجام نشده است.
