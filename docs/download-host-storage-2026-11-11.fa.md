# ذخیره فایل‌های دانشجو روی هاست دانلودی

تاریخ: ۱۱ نوامبر ۲۰۲۶

این تغییر، مسیر ذخیره فایل‌های دانشجو و فایل‌های ضمیمه اتاق را به FTP هاست دانلودی منتقل می‌کند. اطلاعات اتصال از تنظیمات موجود `FileStorage` خوانده می‌شود. برای فعال شدن روی سایت، انتشار API و هر دو فرانت لازم است؛ روی سرور اصلی تغییری اعمال نشده است.

## رفتار آپلود و دانلود

- chunkهای فایل دانشجو در `{FtpRemoteRoot}/private/users/upload-chunks/{uploadId}/` و chunkهای ضمیمه اتاق در مسیر متناظر `rooms` ساخته می‌شوند.
- هر chunk ابتدا به نام موقت روی FTP نوشته و پس از بررسی اندازه نهایی می‌شود. ارسال مجدد همان chunk جایگزینی امن دارد؛ chunk ناقص قابل نهایی‌سازی نیست.
- تجمیع با دو اتصال FTP و بافر ۶۴ کیلوبایتی در حافظه انجام می‌شود. فایل تجمیع‌شده نیز روی FTP است و هیچ فایل chunk یا merge جدیدی روی دیسک API ساخته نمی‌شود. داده همچنان از شبکه API عبور می‌کند؛ این پیاده‌سازی آپلود مستقیم مرورگر به هاست دانلودی نیست.
- فایل نهایی دانشجو در `private/users/files/{userId}/{uploadId}{extension}` و ضمیمه اتاق در `private/rooms/files/{roomId}/...` قرار می‌گیرد. پس از ثبت موفق اطلاعات، پوشه chunk همان آپلود حذف می‌شود.
- مسیرهای multipart محدودیت اندازه و آستانه حافظه دارند تا بافر پیش‌فرض ASP.NET فایل را روی دیسک موقت ننویسد. مسیر مستقیم قدیمی فایل دانشجو تا ۸ مگابایت پذیرفته می‌شود؛ فرانت‌های فعلی برای فایل‌های بزرگ‌تر از مسیر chunk استفاده می‌کنند. سقف فایل دانشجو ۳ گیگابایت و ضمیمه اتاق ۵۰ مگابایت حفظ شده است.
- دانلود FTP نیز دیگر نسخه موقت کامل روی API ایجاد نمی‌کند. HTTP Range با باز کردن اتصال FTP از offset موردنظر پشتیبانی می‌شود.
- مهلت پروکسی ClientWebSite فقط برای مرحله `UploadFileComplete` به یک ساعت افزایش یافته است. محدودیت‌های مستقل IIS، CDN و پروکسی محیط انتشار باید با زمان انتقال فایل‌های حجیم سازگار باشند.

## مصرف فضای هاست

`GET /api/Service/UserFile/GetStorageUsage` فقط برای نقش ادمین قابل استفاده است. در AdminDashboard و ClientWebSite، بالای ابزار آپلود فایل‌های دانشجو، ظرفیت کل، مصرف‌شده و باقی‌مانده نمایش داده می‌شود. این اعداد فضای مشترک حساب هاست هستند و سهمیه مجزای دانشجو نیستند.

ظرفیت بر اساس پاسخ مالک پروژه ۵۰ گیگابایت تنظیم شده است؛ مبنای فعلی `50 × 1024³`، برابر با `53687091200` بایت است. اگر قرارداد هاست ظرفیت ده‌دهی دارد، مقدار دقیق بایت را جایگزین کنید.

```json
{
  "FileStorage": {
    "DownloadHostCapacityBytes": 53687091200,
    "FtpUsageRoot": "/"
  }
}
```

این دو مقدار پیش‌فرض دارند. در متغیرهای محیطی نیز نام‌های `FileStorage__DownloadHostCapacityBytes` و `FileStorage__FtpUsageRoot` قابل استفاده‌اند. اطلاعات ورود FTP را در تنظیمات امن موجود نگه دارید.

مصرف از مجموع اندازه فایل‌های قابل مشاهده حساب FTP در `FtpUsageRoot` محاسبه می‌شود؛ فایل‌های نهایی، آپلودهای نیمه‌تمام و سایر فایل‌های قابل مشاهده حساب را شامل می‌شود. این روش جای گزارش سهمیه پنل هاست را نمی‌گیرد و موارد خارج از دسترسی حساب FTP را نمی‌سنجد. فضای باقی‌مانده برابر ظرفیت تنظیم‌شده منهای این مصرف است و منفی نمایش داده نمی‌شود. هنگام تجمیع، وجود هم‌زمان chunkها و فایل نهایی موقتاً مصرف را افزایش می‌دهد.

پاسخ بک‌اند ۱۵ ثانیه در حافظه cache می‌شود؛ رابط هر ۳۰ ثانیه و پس از تغییر لیست فایل‌ها تازه‌سازی می‌شود و دکمه تازه‌سازی دستی هم دارد. قطع FTP، خطا نمایش می‌دهد و به‌صورت مصرف صفر گزارش نمی‌شود.

## حذف و پاک‌سازی

- حذف فایل و زیرپوشه‌های دانشجو، فایل فیزیکی روی FTP و پوشه chunk متناظر را پاک می‌کند. آپلودهای فعال داخل پوشه حذف‌شده نیز لغو می‌شوند. ثبت نهایی، لغو و حذف از قفل همان نشست آپلود استفاده می‌کنند.
- حذف ضمیمه اتاق نیز پیش از ثبت حذف در دیتابیس، فایل فیزیکی و chunk متناظر را از FTP حذف می‌کند.
- در خطای FTP، حذف موفق گزارش نمی‌شود و اطلاعات دیتابیس برای تلاش مجدد باقی می‌ماند. دیتابیس و FTP تراکنش مشترک ندارند؛ اگر حذف بخشی از فایل‌ها موفق و ادامه عملیات ناموفق شود، با تلاش مجدد حذف تکمیل می‌شود.
- لغو آپلود، پوشه chunk را فوراً حذف می‌کند. سرویس پس‌زمینه هر ۱۵ دقیقه، آپلودهای رهاشده با بیش از ۶ ساعت بی‌فعالیتی را پاک می‌کند. زمان فعالیت در فایل کوچک `activity.utc` روی FTP نگه‌داری می‌شود تا اختلاف منطقه زمانی FTP باعث حذف زودهنگام نشود. نشانگر نامعتبر برای بررسی نگه داشته می‌شود.
- chunkهای قدیمی API در `wwwroot/users/upload-chunks` و `wwwroot/rooms/upload-chunks` نیز پس از ۶ ساعت بی‌فعالیتی پاک می‌شوند. فقط پوشه‌هایی با نام GUID و فایل‌های `.part` بررسی می‌شوند؛ پوشه‌های ناشناخته، پیوندها و محتوای غیرمنتظره حذف خودکار ندارند.
- این مرحله فایل‌های نهایی قدیمی یا فایل‌های merge باقی‌مانده در پوشه موقت نسخه‌های قبلی را به‌طور خودکار جابه‌جا یا حذف نمی‌کند. برای این موارد باید مسیر مهاجرت موجود و فهرست فایل‌های همان محیط بررسی شود.

نشست آپلود همچنان در حافظه یک نمونه API نگه‌داری می‌شود. restart یا انتشار در میانه آپلود نیاز به شروع دوباره دارد؛ chunkهای رهاشده با سرویس پاک‌سازی جمع می‌شوند. در محیط چند نمونه‌ای، نشست‌ها باید به همان نمونه API هدایت شوند.

## اعتبارسنجی

- Release بک‌اند در اجرای تست‌ها ساخته شد. ۸۷ تست پروژه اصلی و ۱۱ تست یکپارچه موفق شدند؛ ۴ تست ارسال واقعی SMTP طبق تنظیمات قبلی اجرا نشدند. از این تعداد، ۱۶ تست جدید رفتار ذخیره‌سازی، کنترل دسترسی ظرفیت، Range و جلوگیری از بافر دیسکی multipart را پوشش می‌دهند.
- چرخه واقعی FTP روی سرور آزمایشی محلی و داده بیش از ۸ مگابایت بررسی شد: chunk ناقص، ارسال مجدد، ترتیب متفاوت ارسال، تجمیع بایت‌به‌بایت، ادامه دانلود، مصرف واقعی فایل‌ها، حذف تکراری، لغو و انقضا موفق بودند. روی FTP اصلی داده آزمایشی نوشته نشده است.
- ۳ تست رابط نمایش ظرفیت موفق شدند. ساخت production داشبورد نیز موفق شد.
- بررسی کامل TypeScript در ClientWebSite با ۹۵ خطای موجود در بخش‌های دیگر متوقف می‌شود. مقایسه با نسخه قبل از این تغییر، همان ۹۵ خطا و صفر خطای جدید نشان داد. این نتیجه به معنی موفق بودن ساخت کامل ClientWebSite نیست.
- هشدارهای موجود ساخت، از جمله ناسازگاری نسخه بسته قدیمی `AutoMapper.Extensions.Microsoft.DependencyInjection`، جدا از این تغییر باقی هستند.

گزارش اجرای محلی، مقایسه TypeScript و نسخه‌های مبنا در `.download-storage-review` نگه‌داری شده‌اند. این پوشه ابزار بررسی توسعه است و نباید همراه برنامه منتشر شود.
